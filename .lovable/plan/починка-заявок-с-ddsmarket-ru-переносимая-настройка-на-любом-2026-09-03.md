# Починка заявок с ddsmarket.ru + переносимая настройка на любом хосте

## Что происходит сейчас (проверено)

- Продакшен собирается статически (`bun run build:pages` → `dist/client`, раздача через `scripts/serve-static.mjs`), поэтому серверного маршрута `/api/public/lead` на сервере просто нет.
- Проверка живого сайта: `POST https://ddsmarket.ru/api/public/lead` возвращает `200` и HTML главной страницы (SPA-фолбэк), а не JSON.
- Форма считает успехом любой `res.ok`, поэтому получает `200` от HTML-страницы, показывает «отправлено» и **никогда** не доходит до резервной отправки в Telegram. Отсюда «заявки не приходят».
- `/health` на домене отвечает `200` — статический сервер работает, дело только в отсутствии API.
- Токен Telegram и chat_id сейчас лежат в коде (и в клиентском бандле) — это надо убрать.

## Что сделаем

1. **Форма перестанет врать об успехе.** Отправку считать успешной только если ответ действительно JSON с `ok: true` (проверка `content-type` + разбор тела). Иначе — переход к резервному каналу.
2. **Отправка станет независимой от хостинга.** В `contacts.tsx` и в кнопке «Оставьте заявку» использовать один общий модуль отправки со списком каналов по порядку:
   - собственный эндпоинт `/api/public/lead` (если хост умеет серверный код);
   - внешний эндпоинт из `VITE_LEAD_ENDPOINT` (задаётся переменной окружения при сборке — можно указать любой воркер/функцию на другом хосте);
   - Telegram напрямую из браузера через `VITE_TG_BOT_TOKEN` / `VITE_TG_CHAT_ID` — только если они заданы при сборке;
   - если ни один канал не сработал — честное сообщение об ошибке и кнопка «Отправить в WhatsApp/Telegram» как ручной путь (заявка не теряется).
3. **Секреты из кода убрать.** Хардкод токена и chat_id удалить из `lead.ts` и `contacts.tsx`; читать только из окружения. Токен, который уже попал в публичный бандл, нужно перевыпустить в BotFather.
4. **Статическая раздача научится принимать заявки.** В `scripts/serve-static.mjs` добавить обработку `POST /api/public/lead`: та же логика, что в серверном маршруте (валидация, honeypot, Telegram, email-копия через Resend), читая `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `RESEND_API_KEY`, `LEAD_EMAIL_FROM`, `LEAD_EMAIL_TO`. Это делает заявки рабочими на текущем сервере без смены схемы деплоя.
5. **Тот же обработчик для nginx-варианта.** В `nginx.conf` проксировать `/api/` на локальный Node-процесс (или задокументировать, что вариант Docker+nginx использует `serve-static.mjs`), чтобы поведение совпадало.
6. **Инструкция по переносу на другой хост.** Файл `docs/leads-setup.md` с готовыми шагами: какие переменные окружения задать, как поднять эндпоинт на Cloudflare Worker / Vercel / любом Node-хосте, как указать `VITE_LEAD_ENDPOINT` при сборке, как проверить доставку `curl`-запросом. Один и тот же бот и email работают на любом хосте, потому что всё определяется только переменными окружения.

## Проверка

- `curl -X POST .../api/public/lead` локально должен вернуть JSON `{"ok":true,...}` и сообщение должно прийти в бот.
- Негативный тест: без переменных окружения эндпоинт возвращает понятную ошибку, а форма показывает ошибку и ручные кнопки, а не ложный «успех».
- `tsgo --noEmit` без ошибок.

## Технические детали

- Новый модуль `src/lib/lead.ts` (клиентская отправка) + общий текст заявки, чтобы не дублировать формат сообщения.
- Логика обработчика заявок выносится в `scripts/lead-handler.mjs`, чтобы её использовали и `serve-static.mjs`, и, при необходимости, отдельный воркер.
- Переменные: серверные — `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `RESEND_API_KEY`, `LEAD_EMAIL_FROM`, `LEAD_EMAIL_TO`; клиентские (опциональные, только для чисто статического хоста) — `VITE_LEAD_ENDPOINT`, `VITE_TG_BOT_TOKEN`, `VITE_TG_CHAT_ID`.
- Дизайн и структура карточек товаров не меняются.
